## Data & confidentiality

**The real SPN/FMI → DTC dictionary and real TATA Motors telematics logs are proprietary.
They are not used, read or reproduced anywhere in this phase.** Every artifact here is
fabricated and carries the label **`synthetic - illustrative`**:

| element | provenance |
|---|---|
| SPN values | invented, all inside the SAE J1939 **manufacturer-proprietary range 520192–524287**, so no value can be mistaken for a real SAE SPN or an OEM assignment |
| FMI values and their meanings | the **public** SAE J1939-73 failure-mode definitions |
| SPN/FMI → P-code pairing | **fictitious**, written for this demonstration |
| vehicle ids, timestamps, occurrence counts | invented (`SYN-VEH-0001`, …) |
| target P-codes | **real** codes from the 3.3L DTC manual, so the downstream manual lookup and the advisory content are genuine (except `P0195-00`, chosen *because* the manual does not contain it) |

Artifacts: `data/synthetic/spn_fmi_dictionary.json` (15 entries),
`data/synthetic/telematics_log.jsonl` (18 rows), generated by
`scripts/gen_synthetic_telematics.py`.

## Framing: functional demonstration, not an accuracy result

This phase demonstrates a **deterministic normalization method** and its **edge-case
coverage**. It is **not** an accuracy measurement, and no number here should be read as one.

A deterministic rule applied to data constructed for that rule resolves "correctly" by
construction: reporting "15/15 mappings resolved, 100%" would be circular and meaningless.
What the run does show is that **every branch of the ladder is reachable and behaves as
specified**, including the branches that must refuse. Accuracy could only be measured against
the real dictionary and real logs, which is Plan-of-Work **Phase 4 (telematics ingestion)** and
is out of scope here. This repository's own Phase 4 is indexing — a different thing with the
same number.

## 1. The normalization ladder — `src/normalize.py`

```
SPN + FMI  ->  P-code  +  DTC low byte  ->  code_full  ->  keyed manual entry  ->  advisory
```

The **DTC low byte** is the failure-type byte, which is exactly the manual's suffix:
`P0192` + low byte `00` → `P0192-00`. The demo includes a non-`00` low byte (`P0100-9C`) so
this is not quietly assumed.

The first rung that applies wins. Every rung is recorded in a trace.

| rung | condition | outcome |
|---|---|---|
| **R0** validate | `spn` int 0–524287 (19-bit), `fmi` int 0–31, `occurrences` int ≥ 1, ISO-8601 timestamp, non-empty `vehicle_id` | fail → `REJECTED_MALFORMED` (logged, no advisory) |
| **R0** de-duplicate | identical (`vehicle_id`, `timestamp`, `spn`, `fmi`) already seen | `DUPLICATE_SKIPPED` |
| **R1** exact (spn, fmi) | in the dictionary → `code_full` → `Retriever.retrieve(code_full)` | `exact_code` → **`ADVISORY`** (deterministic fix block) |
| | | `suffix_not_found` → `CLARIFY_LOW_BYTE` (9.3b: variants listed, no procedure) |
| | | `unknown_code` → `REFUSED_NOT_IN_MANUAL` (9.3b: explicit refusal) |
| **R2** SPN known, FMI unmapped | all mapped entries of that SPN, ordered by \|FMI − mapped FMI\| then FMI; the nearest is marked | `FALLBACK_CANDIDATES` (**no advisory**) |
| **R3** SPN unknown | nothing to map | `UNMAPPED_NO_ADVISORY` (logged) |

The manual is reached **only** through `Retriever.retrieve(<code>)` — the production exact-code
router, including the Phase 9.3b refusal and clarification behaviour — and advisories reuse
`advise.fix_block` from Phase 9.1. Nothing is generated by a model.

### Why a fallback never becomes an advisory (`ADVISE_ON_FALLBACK = False`)

An FMI is a **failure mode**, and numerically adjacent FMIs are often opposite faults. The
synthetic data makes the trap concrete: for SPN 520210, FMI 5 is unmapped and its numerically
nearest mapped FMI is 4 → `P0192-00` *short circuit to ground*. But FMI 5 means "current below
normal **or open circuit**", and in this manual open circuit is covered by `P0193-00` (*short
circuit to battery or open circuit*), which is FMI **3** here — two steps away, not one.
Auto-serving the nearest FMI would assert a repair procedure for a fault that was not reported.
The ladder therefore surfaces candidates for a technician to confirm, the same policy as the
9.3b "did you mean" suggestions: **surfaced, never auto-selected**.

## 4. End-to-end demo rows

Reproduce with `PYTHONPATH=src .venv/bin/python src/normalize.py --demo`.

### (a) Complete mapping → advisory

Input row: `{"timestamp": "2026-03-02T08:14:05Z", "vehicle_id": "SYN-VEH-0001", "spn": 520210, "fmi": 4, "occurrences": 3}`

```
R0 validate            ok
R0 de-duplicate        new
R1 exact (spn,fmi)     hit  p_code=P0192 dtc_low_byte=00 code_full=P0192-00
R1 manual lookup       exact_code (by_code_full)
OUTCOME: ADVISORY — SPN 520210 FMI 4 -> P0192-00: manual entry found.

P0192-00 — Rail pressure Sensor Short circuit to ground
  System: rail_pressure   |   Manual page 8
  Effect on vehicle: Torque reduction
  Likely causes: 1. Wiring Harness problem  2. Sensor failure  3. Sensor connector problem
  Troubleshooting steps:
    Step 1: Check the battery voltage   [spec: 12.5±3 volts]
    Step 2: Check connector if rail pressure sensor is connected properly to the wire harness connector
    Step 3: If connector found lose in step 2 then fix is properly & go to Step 13  -> if yes -> Step 13
    ...
  Source: P0192-00, manual page 8.
```

The advisory content is the real manual record with its branch logic and page citation.

### (b) Fallback: SPN known, FMI unmapped → candidates, no advisory

Input row: `{"timestamp": "2026-03-02T10:11:12Z", "vehicle_id": "SYN-VEH-0001", "spn": 520210, "fmi": 5, "occurrences": 2}`

```
R1 exact (spn,fmi)          miss
R2 spn-only / nearest-fmi   candidates n=3 nearest_fmi=4 advise_on_fallback=False
OUTCOME: FALLBACK_CANDIDATES

SPN 520210 is known but FMI 5 (current below normal or open circuit) has no mapping.
No advisory is issued: an FMI is a failure mode and a neighbouring FMI may be a
different fault. Candidates for a technician to confirm:
P0192-00 (FMI 4, nearest), P0193-00 (FMI 3), P0194-00 (FMI 2).
```

### (c) Mapped P-code absent from the manual → explicit refusal (9.3b), never fabrication

Input row: `{"timestamp": "2026-03-02T11:00:00Z", "vehicle_id": "SYN-VEH-0003", "spn": 520260, "fmi": 4, "occurrences": 1}`

```
R1 exact (spn,fmi)   hit  code_full=P0195-00
R1 manual lookup     unknown_code (no match in either code index)
OUTCOME: REFUSED_NOT_IN_MANUAL — DTC P0195-00 is not covered in this manual.
```

### (d) Low byte absent → clarification listing the known variants

Input row: `{"timestamp": "2026-03-02T11:05:00Z", "vehicle_id": "SYN-VEH-0001", "spn": 520220, "fmi": 16, "occurrences": 1}`

```
R1 exact (spn,fmi)   hit  code_full=P0116-13
R1 manual lookup     suffix_not_found (by_dtc_code; all suffix variants)
OUTCOME: CLARIFY_LOW_BYTE

Exact code P0116-13 was not found in this manual. Known variants of P0116: P0116-00.
Please confirm the full code.
```

### (e) Unmappable and malformed

```
SPN 520299 FMI 4          -> UNMAPPED_NO_ADVISORY: not in the dictionary; no advisory. Logged.
spn="abc"                 -> REJECTED_MALFORMED: spn missing or not an integer ('abc')
fmi=40                    -> REJECTED_MALFORMED: fmi 40 outside 0..31

```

## 5. What this does and does not establish

**Does:**

- A telematics fault record can be normalised to a manual-keyed entry by a **deterministic,
  fully traced** rule, with no model involved in the mapping.
- The multi-source path works end to end: synthetic telematics row → normalization → real
  manual record → deterministic advisory with page citation.
- The **safety behaviour composes**. Phase 9.3b's refusal and clarification are reused rather
  than re-implemented, so a fault code the manual does not cover produces an explicit refusal
  from the telematics path too, and an unmapped FMI produces candidates instead of a guess.
- Malformed and duplicate rows are rejected and logged, not silently dropped or half-processed.

**Does not:**

- Measure accuracy of any mapping. The dictionary is fictitious; a deterministic rule on data
  built for it is right by construction.
- Validate real SPN/FMI semantics, J1939 transport decoding, freeze frames, occurrence-count
  logic, multi-fault prioritisation or lamp status.
- Show anything about real telematics data quality.

**Next (Plan-of-Work Phase 4 — telematics ingestion, not built):** the real dictionary under
NDA, J1939/FMS decoding, live feed ingestion, dictionary-coverage and mapping-accuracy
measurement against real logs, and prioritisation when one vehicle reports many faults at once.
